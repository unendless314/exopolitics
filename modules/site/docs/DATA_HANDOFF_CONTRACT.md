# Data Handoff Contract: `publish_export` to `site`

**Updated:** 2026-08-18

This document defines how the `site` module consumes the output artifacts generated by the `publish` module. 

The `site` module is a downstream consumer only. It does not perform database writes and relies entirely on these static files as its single source of truth (canonical authority).

---

## 1. Input Sources

All data inputs are located under `data/publish_export/` in the workspace root. The export root is a versioned layout:

```text
data/publish_export/
  current.json                       # atomic pointer; the only reader entry point
  generations/<generation-id>/
    stats.json
    meta.json                        # publish-owned diagnostics; not consumed by the site
    <language_code>/index.json  items/  archives/
```

Readers enter exclusively through the pointer. `current.json` carries `{generation, export_completed_at, last_successful_run_at, languages, content_fingerprint}`; all artifact paths below are relative to the resolved live generation root `generations/<generation-id>/` (written as `<live_generation>` in the rest of this document). Generation ids follow the strict Windows-safe format `YYYY-MM-DDTHH-MM-SSZ` (plus a `-rN` suffix on same-second collisions) and are validated before any path join. Generation directories are immutable once moved in; a no-change publish run only atomically refreshes the pointer's `last_successful_run_at` without building a new generation.

Resolution and ingestion hard-fail (see `BUILD_AND_ROUTING_POLICY.md` section 4) when:

- `current.json` is missing, unreadable, unparseable, or missing required fields
- the generation id violates the strict format (no arbitrary string is ever joined into a path)
- a pointer timestamp is calendar-impossible (e.g. `2026-02-30T12:00:00Z`, which JavaScript would otherwise silently roll over)
- `languages` is empty — the pointer is the authoritative language set for consumers
- the referenced generation directory does not exist
- any expected artifact within the resolved generation is missing, unparseable, or fails schema validation (the per-file rules below)

Every configured language always has `index.json` and `archives/index.json` (each possibly `[]`) plus `items/` and `archives/` directories, even when empty — a language with no published items is a valid, complete export, not a missing file.

The committed development fixture (`tests/fixtures/publish_export/`) follows the same generationized layout: a root `current.json` plus `generations/2026-07-22T03-00-00Z/` holding the former flat contents (the generation id is derived from the fixture stats timestamp; the pointer fingerprint is a format-valid placeholder because only the publish module computes real fingerprints).

The `site` module reads the following files within the resolved live generation:

### 1.1 Language Index Catalog
- **Path**: `<live_generation>/<language_code>/index.json`
- **Purpose**: Provides the latest published items sorted by date.
- **Fields**:
  - `slug` (string): Stable route identifier. Must match the slug format contract in Section 1.6.
  - `display_title` (string): Title of the post.
  - `summary_short` (string): Short preview text.
  - `canonical_url` (string): Original source URL.
  - `source_published_at` (string): UTC ISO-8601 timestamp of publication.
  - `approved_at` (string): UTC ISO-8601 approval timestamp.
  - `published_at` (string): UTC ISO-8601 export timestamp.
- **Note**: Always present for every configured language, possibly `[]`.

### 1.2 Monthly Archive Catalog
- **Path**: `<live_generation>/<language_code>/archives/archive_YYYY_MM.json`
- **Purpose**: Grouped monthly posts.
- **Fields**: Identical array structure to `index.json`.

### 1.3 Monthly Archive Manifest
- **Path**: `<live_generation>/<language_code>/archives/index.json`
- **Purpose**: Manifest listing available monthly archives. Always present for every configured language — `[]` when the language has no archived months.
- **Fields**:
  - `archive_month` (string): Format `YYYY-MM`.
  - `file_name` (string): Name of the monthly JSON archive.
  - `item_count` (integer): Total items in the archive.
  - `updated_at` (string): UTC ISO-8601 timestamp of the last content-changing write to that month.

### 1.4 Detailed Item JSONs
- **Path**: `<live_generation>/<language_code>/items/<slug>.json`
- **Purpose**: Holds the full structured content of individual posts.
- **Fields**:
  - `source_item_id` (integer)
  - `language_code` (string)
  - `slug` (string)
  - `display_title` (string)
  - `summary_short` (string): Single-paragraph summary. Written as the first paragraph of the generated Markdown body and read directly as the SEO description source.
  - `bullets` (object or null): Semantic content slots. For `downstream_action = "publish_summary"`, an object with exactly the three keys `key_claim`, `evidence_level`, and `objective_impact`, each a non-empty string. For `downstream_action = "publish_link"`, always JSON `null` — never omitted, never an empty object.
  - `canonical_url` (string)
  - `source_published_at` (string)
  - `approved_at` (string)
  - `published_at` (string)
  - `downstream_action` (string)
  - `disclosure_note` (string): AI generation or curation note.
  - `author_metadata` (object): Deserialized metadata (contains `source_module`, `writer_type`, and optional `editor` fields).
- **Note**: The item JSON no longer carries a pre-spliced `content` Markdown body, and it never contains presentation label text. The site adapter assembles the Markdown body from `summary_short` and `bullets`, applying locale-specific post labels at build time (see Section 2.2).

### 1.5 Global Stats
- **Path**: `<live_generation>/stats.json`
- **Purpose**: Aggregate statistics.
- **Fields**: Maps of active/withdrawn items, oldest archives, and last run timestamp.
- **Timestamp Semantics**: `last_export_run_timestamp` is frozen at the generation's build time — it identifies when this generation's content was produced, not when the pipeline last ran. The run freshness signal ("last updated", displayed by the Footer and the stats page) is the pointer's `current.json.last_successful_run_at`, which advances on every successful publish run, including no-change runs. `stats.json` itself is still loaded and schema-validated at build time (hard-fail preserved).

### 1.6 Slug Format Contract
- **Ownership**: Canonical slug generation is owned by `publish` (`slugify()` / `generate_slug()`). The `site` module never recomputes, sanitizes, or rewrites slug values — it only rejects non-conforming ones.
- **Format**: Every `slug` field (catalog items and detail item JSONs) must match:

  ```text
  ^[a-z0-9][a-z0-9-]*$
  ```

  ASCII lower-case alphanumerics and hyphens, never starting with a hyphen. This keeps slugs safe as route parameters and as generated-Markdown file names (no path separators, no `.`/`..` segments, no absolute paths).
- **Empty-After-Normalization Fallback**: When a title yields no ASCII characters after normalization (e.g. a purely CJK title), `publish` falls back to `item` (or `item-N` when deduplication requires a suffix). These fallback values conform to the same format rule above.
- **Site-Side Enforcement**: The site adapter (`scripts/lib/post_adapter.js`) validates every item slug against this rule at the filesystem boundary and hard-fails the build on any violation.

## 2. Ingestion Mapping (Phase 1)

During Phase 1 (Build-time JSON-to-Markdown adapter), properties from the detailed item JSON are mapped to Markdown frontmatter as follows:

| JSON Field / Source | Markdown Frontmatter Key | Description / Mapping Rule |
| :--- | :--- | :--- |
| `display_title` | `title` | Title of the post. |
| `source_published_at` | `publishDate` | Converted to a JavaScript Date object. |
| `summary_short` | `description` | Validated single-paragraph summary, used directly as the SEO meta description. |
| `canonical_url` | `canonicalUrl` | Link to the original source. |
| `disclosure_note` | `disclosureNote` | AI authorship and curation disclosure statement. |
| `author_metadata` | `authorMetadata` | Deserialized author/editor metadata object. |

### 2.1 SEO Description Mapping Rule
The item JSON guarantees a validated `summary_short`, so the frontmatter `description` key is taken directly from `item.summary_short`. The former fallback cascade is removed entirely: the adapter must not build a `summaryMap` from the language index catalog (`index.json`), the archive manifest, or archive item files, and the `summaryMap -> content first paragraph -> title` fallback chain no longer exists. This avoids duplicate I/O and a second, divergent summary semantic.

The Markdown file body below the frontmatter block is assembled from the structured fields: `summary_short` becomes the first paragraph, and when `bullets` is present the adapter appends a bullet list using the locale-specific post labels (see Section 2.2). There is no `content` field to fall back to.

### 2.2 Post Label Ownership (Adapter-Only)
The three UI label strings used for the bullet list (`key_claim`, `evidence_level`, `objective_impact`) exist only in `modules/site/src/config/post_labels.json`. This file is the single source of truth for post label text: it is read by `loadPostLabels()` in `modules/site/scripts/lib/post_adapter.js`, and the adapter writes the labels into the generated Markdown; Astro pages must not duplicate the same label keys in `uiTranslations`. Because label text lives only in the site's locale data, changing label wording requires only a site rebuild — no re-translation and no changes to the publish export.

## 3. Phase 2: Page-to-Source Data Mapping

To implement the hybrid ingestion strategy and keep the build memory footprint predictable, pages are mapped to their specific `publish_export` data files. Developers must strictly follow these mappings instead of introducing ad-hoc collection loading queries.

### 3.1 Homepage / Timeline Page
- **URL Path**: `/[lang]/`
- **Data Source**: `<live_generation>/<lang>/index.json`
- **Ingestion Policy**: Read this pre-sorted index file directly using Node.js `fs`. Do NOT call `getCollection("posts")`.
- **Field Usage**: Parse only metadata fields (such as `slug`, `display_title`, `summary_short`, `source_published_at`, `canonical_url`) to build the timeline view. Map these fields to the Timeline component. Limit the page to the latest 300 entries.

### 3.2 Monthly Archive Index Page
- **URL Path**: `/[lang]/archives/`
- **Data Source**: `<live_generation>/<lang>/archives/index.json`
- **Ingestion Policy**: Read the monthly archive manifest directly. The manifest is always present (possibly `[]`).
- **Field Usage**: Render the months (e.g., `YYYY-MM`) and item counts dynamically from the manifest list.

### 3.3 Monthly Archive Detail Pages
- **URL Path**: `/[lang]/archives/[month]/`
- **Data Source**: `<live_generation>/<lang>/archives/archive_YYYY_MM.json`
- **Ingestion Policy**: Read the specific monthly archive JSON file.
- **Field Usage**: Map the item array to list the posts for that month. No full article bodies are read.

### 3.4 Post Detail Pages
- **URL Path**: `/[lang]/posts/[slug]/`
- **Data Source**: 
  - *Route Generation*: `<live_generation>/<lang>/index.json` or `getCollection("posts")` (used solely to discover paths).
  - *Content Source*: `<live_generation>/<lang>/items/<slug>.json` (mapped to `src/content/posts/generated/[lang]/[slug].md` via the adapter script).
- **Ingestion Policy**: 
  - In `getStaticPaths()`, the return array MUST only populate lightweight identifiers inside `props` (i.e. `{ id: post.id }`). Do NOT pass the full `post` object.
  - During page rendering, dynamically import `astro:content` and query `getEntry("posts", id)` to load the specific post content into memory. This ensures only active pages reside in RAM during rendering.

### 3.5 Global Statistics Page
- **URL Path**: `/stats/` (or `/[lang]/stats/`)
- **Data Source**: `<live_generation>/stats.json` (plus `data/publish_export/current.json` for the freshness signal)
- **Ingestion Policy**: Read this single global statistics file directly.
- **Field Usage**: Display aggregate statistics (e.g., total active items) on the stats board. The "last updated" timestamp is read from the pointer's `last_successful_run_at`, not from the frozen in-generation `stats.json.last_export_run_timestamp` (see Section 1.5).
